# LLM-помощник для создания онтологий ЭЗОП

**Статус:** черновик требований

**Версия:** 0.1

**Этап:** MVP — чат-помощник по шаблонам

## Цель

Помочь пользователям описывать предметную область на формальном языке ЭЗОП. Пользователь объясняет задачу на естественном языке, а LLM помогает выбрать доступные в текущей среде шаблоны, разобраться в их применении и подготовить фрагмент текста онтологии.

## Проблема

Правила использования шаблонов легко забыть. Новому пользователю также трудно понять, какие шаблоны подходят для его предметной области и как их записать.

В интерфейсе уже есть словарь шаблонов, редактор онтологии и действие «Построить онтологию». Требуется связать эти возможности с диалогом на естественном языке, сохранив существующий способ работы ЭЗОП с онтологиями.

## MVP

Добавить в интерфейс окно чата, связанное с текущей средой онтологии.

Пользователь может:

1. Описать предметную область или задать вопрос о формальном языке ЭЗОП.

2. Получить объяснение и рекомендации по подходящим шаблонам.

3. Попросить LLM предложить фрагмент текста онтологии.

4. Просмотреть предложенный текст и явно вставить его в редактор онтологии.

5. Продолжить диалог с учётом предыдущих сообщений текущего сеанса.

В первом этапе чат **не строит, не сохраняет и не публикует онтологию автоматически**. Пользователь сам решает, когда вставить текст и нажать «Построить онтологию».

## Контекст модели

Контекст LLM должен соответствовать словарю шаблонов активной среды онтологии.

- Имена шаблонов доступны интерфейсу через `window.serverData.templates`.

- Описание выбранного шаблона уже запрашивается у сервера ЭЗОП через существующую интеграцию.

- Для MVP использовать описания релевантных шаблонов, полученные через имеющийся серверный механизм.

- Не добавлять в MVP отдельную векторную базу, RAG-платформу или многоагентный фреймворк.

- В системной инструкции явно указать: не выдумывать имена шаблонов и синтаксические правила; при недостатке контекста задавать уточняющие вопросы.

Источником формальной проверки остаётся вычислительное ядро ЭЗОП, а не ответ модели.

## Интеграция с GigaChat

Для MVP использовать GigaChat API. Предварительно выбранная модель — `GigaChat-3-Ultra`.

Перед реализацией проверить, что для используемого API-аккаунта доступны нужная модель, авторизация и заявленный бесплатный режим. Согласно текущей документации для физических лиц, бесплатные квоты разделены по моделям и действуют 12 месяцев; условия и порядок подключения могут измениться.

- [Тарифы GigaChat API для физических лиц](https://developers.sber.ru/docs/ru/gigachat/tariffs/individual-tariffs)

- [Авторизация и REST API GigaChat](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/gigachat-api)

### Серверная часть

API-ключ и получение токена GigaChat должны находиться на стороне Drupal-сервера. Ключ нельзя включать во фронтенд, отдавать браузеру или коммитить в репозиторий.

Добавить на стороне Drupal серверный маршрут-посредник, который:

1. Принимает сообщения чата и контекст релевантных шаблонов от фронтенда.

2. Выполняет запрос к GigaChat API.

3. Возвращает ответ в согласованном формате.

4. Возвращает понятную ошибку, если API недоступен, превышена квота или не пройдена авторизация.

Маршрут и формат запроса согласовать с существующей Drupal-интеграцией. В React разместить вызов рядом с остальными HTTP-запросами в `src/redux/helpers/request.ts`; состояние чата оформить в Redux в соответствии с архитектурой проекта.

Фронтенд виджета ожидает URL маршрута в `window.serverData.llmChatUrl`. Он отправляет JSON с полями `messages` (массив `{ role, content }`), `templates` (имена шаблонов активной среды) и `env_id`. Успешный ответ должен содержать строковое поле `reply`. Drupal должен сформировать системный контекст по активной среде и сохранить секреты GigaChat на сервере.

## Интерфейс и поведение

- Чат открывается отдельной небольшой кнопкой с иконкой, закреплённой в правом нижнем углу окна браузера.
- По нажатию поверх страницы раскрывается компактная панель чата; она не меняет размеры и расположение редактора, словаря, запросов и логов.
- Панель можно свернуть обратно в кнопку и открыть снова. Сообщения и текущий ввод сохраняются при сворачивании в пределах открытой страницы.
- Панель адаптируется к небольшим экранам и не выходит за пределы видимой области.
- Для MVP достаточно одного размера раскрытой панели; отдельный полноэкранный режим не требуется.

- Диалог ведётся на русском языке.

- Во время запроса отображается состояние ожидания; ошибки API видны пользователю.

- Текст, предложенный моделью, можно проверить до вставки.

- Вставка в редактор выполняется только по явному действию пользователя.

- Историю диалога в MVP хранить только в состоянии текущей страницы; долговременное хранение и отдельная серверная база не нужны.

## Последующий этап: проверка через ядро

После MVP можно добавить явную проверку предложенного текста через существующее построение онтологии:

1. Пользователь запускает проверку.

2. Интерфейс отправляет текст в ядро и показывает результат.

3. При ошибке предлагает модели объяснить её и подготовить исправленный вариант.

4. Пользователь просматривает исправление и подтверждает следующую проверку.

Перед реализацией этого этапа изучить побочные эффекты `requestBuildOntology`: при отсутствии `curcnpt_id` текущая логика может сначала сохранить черновик. Не запускать автоматические повторные построения, пока не подтверждено безопасное поведение. Если позднее появится автоматический цикл исправлений, ограничить число попыток и оставить пользователю просмотр результата.

## Ограничения проекта

- Фронтенд — legacy-приложение на React 16, TypeScript 3.7 и Redux.

- Drupal и вычислительное ядро находятся за пределами репозитория фронтенда; доступ к Drupal есть.

- Не менять серверные URL, путь сборки, обработку Windows-1251 и существующий протокол ядра без отдельной необходимости.

- Не модернизировать стек и зависимости в рамках этой задачи.

- Разработку разделить на изменения фронтенда и Drupal, документируя оба набора изменений.

## Критерии готовности MVP

- Пользователь может вести диалог с LLM из интерфейса ЭЗОП.

- Ответы учитывают описания шаблонов активной среды.

- Модель может объяснить выбор шаблона и подготовить формальный фрагмент.

- Предложенный текст не меняет редактор до явного подтверждения пользователя.

- Ошибка или недоступность API показывается понятно; чат и редактор остаются работоспособными.

- API-ключ и токен не попадают в браузерный код и репозиторий.

- Для затронутого фронтенда проходят `yarn lint` и `yarn check-types`; при изменении сборки или ассетов также выполняется `yarn build`.
